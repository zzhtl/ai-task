# 0009. 远端工具代理：模型的每一次远端动作都要回中心

## 状态

已接受（2026-09-09）。

## 决策

AI 节点声明了远端主机时，它拿到的工具是 `mcp__ai_task_remote__remote_{bash,read,write,glob}`
四个，**本地的 Bash / Read / Write / Edit / Glob / Grep 全部去掉**。

代理是一个 stdio MCP server（`ai-task mcp-proxy`），由 Claude Code 按节点拉起。
它把每次调用打到中心的 `POST /internal/remote/call`，中心先判策略、再经 SSH
下发给目标机上的 agent。

### 为什么本地工具必须去掉

这是远端执行里最容易出、也最难查的错。本地工具留着的话，模型会在**中心机**上
老老实实执行 `Bash`/`Write`，而它以为自己操作的是目标机。没有任何报错，
只有做错了的事——在错误的机器上。

`a_remote_ai_node_loses_every_local_filesystem_tool` 这条测试钉住它。

### 为什么代理不自己连 SSH

代理是 Claude Code 拉起的子进程，它的命令行和环境对模型是可见的。
凭据留在中心，代理手里只有一个 run 级令牌和中心地址——它能做的事就只有
"请中心代为执行"。

`ProxyConfig` 用穷举解构做了编译期守卫：加一个字段就编译不过，
逼着加字段的人先想清楚这个字段该不该出现在那个进程里。

### 目标主机由中心从任务定义里取

代理不能指定主机，请求里也没有这个字段。否则模型只要换一个 host_id，
就能绕开所有按 tag 生效的策略（比如"prod 机上写类操作一律 ask"）。

节点名钉在代理的启动参数里（一个节点一次 CLI 调用，也就一个 MCP server 进程），
中心据此从任务版本快照里查出该节点声明的主机。节点没声明主机就直接拒绝，
**不落回中心本机**——那是把远端操作悄悄变成了本地操作。

### 两道关卡必须对同一个工具名做判决

Claude Code 的 `PreToolUse` hook 把 MCP 工具报成 `mcp__<server>__<tool>`，
而代理自己上报的是 `remote_write`。不归一的话，同一个动作在两道关卡上匹配的是
**不同的规则**。

实测撞到过：写着 `tool: "remote_write"` 的策略在 hook 那道完全不命中，
审计日志里出现了「seq 15 allow、seq 16 deny」这种自相矛盾的记录。这次是安全的
（第二道拦住了），但反过来的情形才是真正危险的——有人以为 hook 会拦住，
于是没在别处设防。

`normalize_tool()` 只剥我们自己 server 的前缀，别人的 MCP server 同名工具
不能借我们的规则名混过去。

### 策略拒绝不是 HTTP 错误

`/internal/remote/call` 对被拒绝的调用返回 200 + `executed: false` + 原因。
返回 4xx 会让 MCP 客户端把它当成传输故障，模型只会原样重试。

拒绝原因作为工具结果回给模型（标成 `is_error`），让它自己调整。实测中模型
读到"巡检任务禁止改目标机上的任何文件"之后，直接在结构化输出里报了
`wrote_report: false` 并说明原因，而不是反复重试。

### 路径与内容都不进命令行解析

路径用单引号包裹（POSIX shell 单引号内无转义，只需处理单引号本身）。
写文件的内容走 heredoc 从 stdin 进，不进命令行：几十 KB 会撑爆 `ARG_MAX`，
而且任何引号处理都可能被内容本身骗过去。heredoc 的结束标记会避开内容里
已有的同名串。

引法的测试是拿真 `sh` 跑一遍 `printf %s`，断言语义而不是字面量——
换个等价写法时测试不该变红。

## 代价

一次远端工具调用要走：模型 → 代理进程 → 中心 HTTP → 策略（一次数据库读）
→ SSH → agent。比直连多两跳。

值得，因为这两跳换来的是"每个远端动作**必然**流经策略"这个结构性保证。
hook 是第二道，覆盖内置工具并统一 deny 的反馈格式。两道都要。
