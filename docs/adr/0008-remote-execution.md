# 0008. 远端执行：推送一个 agent，凭据留在中心

## 状态

已接受（2026-09-09）。

## 决策

目标机上只有一个 musl 静态二进制 `ai-task-agent`（570 KB），通过 SSH 投送。
**没有 Node、没有 Python、没有 API key。**

中心与 agent 之间是一条 SSH exec channel 上的行分隔 JSON。协议里只有六个操作：
`hello` / `exec` / `read` / `write` / `glob` / `shutdown`。

### 本机执行也走 agent

`HostSelector::Local` 不是"直接 `Command::spawn`"。本机同样起一个 agent 子进程，
走同一套协议、同一个二进制。

换来两件事：本机执行同样有资源归因和资源上限（本机通常有 systemd，
上限是真的强制的）；以及只有一条代码路径要维护——只在远端才会暴露的 bug，
本地跑测试就能撞见。

代价是每个 shell 节点多一次进程创建，量级是毫秒。

### agent 按内容哈希命名并复用

`ai-task-agent-<sha256 前 16 位>`。投送前先 `sha256sum` 探一次，一致就跳过上传；
需要上传时先写 `.tmp`、校验哈希、再原子 `mv`。

版本由哈希唯一确定，不存在"那台机器上是哪个版本"的问题。中断的传输留下的是
一个 `.tmp`，不会是一个半截的可执行文件。

### host key 只放宽"没见过"这一档

`HostKeyPolicy` 只有 `Strict` 和 `AcceptNew` 两种，**没有"接受任意密钥"**。
`AcceptNew` 是 TOFU：第一次见到一台主机就记下它的密钥。

密钥**变了**在任何配置下都是拒绝——那才是中间人攻击的信号。

russh 的 `check_known_hosts_path` 在这里很容易读反：`Ok(false)` 是"没有这条记录"
（TOFU 场景），密钥对不上是 `Err(KeyChanged)`。读反的后果是拒绝所有首次连接、
同时接受所有被换掉的密钥。`classify()` 把这个映射连同测试一起钉住了。

### 凭据加密落库，没有密钥服务就不启动

SSH 私钥用 chacha20poly1305 加密后存 `credentials` 表，每条密文一个随机 nonce。
KEK 来自 `AI_TASK_ENCRYPTION_KEY`（64 位十六进制），**缺了进程直接退出**。

不提供"先明文存着，以后再加"的降级：已经明文写进去的私钥不会自己变成密文，
而这个降级一旦上线就再也摘不掉。启动失败很吵，但它发生在加第一台机器之前。

任何读接口都不返回私钥。`HostSummary` 有一个字段清单的测试，加字段会让它失败。

## 资源归因

三档，按目标机的能力降级：

| 档位 | 机制 | 上限强制 | 归因完整度 |
|---|---|---|---|
| `systemd` | `systemd-run --user --scope` + cgroup v2 | 是 | 完整（含 `memory.peak`） |
| `proc` | `/proc/<pid>/stat` 进程树遍历 | **否** | 缺已退出进程的峰值 |
| `none` | 无 | 否 | 只有任务状态 |

降级会发一条 `resource_degraded` 事件，界面上标红。**这条必须显式发出来**：
`proc` 档下 `MemoryMax` 根本没有被强制，不标出来的话用户会以为限额生效了。

`proc` 档要把 `cutime`/`cstime` 一起算进去。只看 `utime`/`stime` 会漏掉所有已经
被回收的短命子进程——`sh -c` 里循环调 `date` 的脚本能因此少记一半 CPU。

### 采样边采边落库，不攒到最后

1 Hz 采样直接进 `run_metrics`（1 秒 / 8 个点攒一批）。

不攒到命令结束再一次性写，原因有二：跑几十分钟的任务要等结束才有曲线的话，
"实时监控对服务器的影响"就无从谈起；而且连接一断，攒在内存里的点会一起消失
——那恰恰是最需要看曲线的时候。

只有当整条命令比一个采样周期还短、一个点都没采到时，才补一条终态用量。
无条件补的话，每条 CPU 曲线末尾都会多一段掉到零的假下降（进程已退出，
它和上一个采样点之间的 CPU 增量本来就是 0）。

### OOM 被杀时报的是上限，不是采到的峰值

进程可能在两次采样之间就冲到上限被杀，那时 cgroup 已经没了，`memory.peak` 读不回来。
报采样到的高水位会得到"命中 512 MiB 上限（峰值 13 MiB）"这种自相矛盾的话。
确定为真的是申报的上限。

资源击穿落 `RunStatus::ResourceExceeded`，与普通 `Failed` 分开——
"机器扛不住"和"任务写错了"要能在界面上一眼分开。

## SSH 断开

一条 exec channel 对应一次节点执行。连接断了命令就没了，**不做续跑**——
那需要 agent 侧的会话持久化和输出缓冲，是另一个特性。

能保证的是：run 不会挂住（1 秒内落终态）、错误是可辨认的传输错误
（"agent 连接已断开"而不是一个业务失败）、已经采到的点全部在库里、
事件 seq 连续。之后由节点的 retry 策略决定要不要重来。

实测：断开 31 秒，第 1 次尝试报连接断开、第 2 次报 Connection refused、
第 3 次连上并跑完；事件 seq 1..10 无断号，两次尝试的 28 个采样点都在，
时间轴上能看见中间那段空档。

## 替代方案

**在目标机上装 Claude Code**：目标机要有 Node 和 API key。一台生产机上放一把
能调用模型的密钥，是把爆炸半径从"这次执行"扩大到"这台机器的整个生命周期"。

**纯 SSH 命令拼接，不投送 agent**：省掉一个二进制，但拿不到资源归因、
拿不到资源上限、路径根约束只能靠字符串检查（挡不住符号链接），
而且每个操作一次 SSH 往返。
